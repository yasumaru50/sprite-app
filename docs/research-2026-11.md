## 1. 今の方針と先行事例の照らし合わせ

次の方針は、先行事例（待機アニメの解説・ドット絵の動きのツール）と同じ向きだった（未確認）。変える理由は見つからなかった。

| 今の方針 | 先行事例での扱い |
| --- | --- |
| 全フレームを同じ大きさにする | シートを等間隔で切るエンジン・ツールが多く、大きさをそろえるのが前提 |
| 作れないときは動かさない（警告だけ） | 崩れたフレームを出すより、動きを付けない方がよいとする例がある |
| 2〜4 フレームの控えめな待機 | 待機の動きは少ないフレーム数で、1 ドットの上下が基本 |
| 整数のドットだけで動かす（拡大・回転・ぼかしをしない） | 半端な位置・回転はドットが崩れるので避ける |
| 手足の動き（歩き・攻撃）は自動でやらない | 骨（ボーン）で動かすツールでも、隠れる部分は人が描き足す前提（PixelOver） |

## 2. グリッド検出

- **いくつかの方法を合わせる**: 1 つの方法だけで決めず、「同じ色の続く長さ」「輪郭（勾配）の強さの並び」「ずらしたときの似かた（自己相関）」
  など複数の推定を出し、突き合わせて決める例がある
- **大きさと位置（ずれ）を両方推定する**: ドットの大きさだけでなく、格子の始まりの位置も求める
- **2 倍・半分の取り違えに気を付ける**: 周期の推定は、本当の大きさの 2 倍（2 ドットを 1 ドットと見る）や半分を拾いやすい。
  候補ごとに実際に格子を当てはめ、マスの中の色のばらつきで比べて確かめる例がある（8. の proper-pixel-art）
- **縦と横は別々に推定する**: 軸ごとに推定してから、正方形とみなすかを決める
- 私たちの `retrocore/sprite/grid.py` との違いは 8. にまとめた

## 3. 縮小（マスの色の決め方）

- マスの**平均色を使わない**。平均は元の絵に無い中間色を作るため
- 代わりに、**マスの中でいちばん多い色**を選ぶか、**マスの中心に近い画素を重く見て**色を決める（縁はぼけ・半ドットのずれの影響を受ける）
- 私たちの状況:
  - 普通のイラストの縮小（`retrocore/sprite/downscale.py`）は、すでに実在する画素の色だけを使っている（方針どおり）
  - グリッド検出のマスの色（`grid.py` の手順 5）は、中心寄りの重み＋最頻色までは同じ考え方だが、最後に「最頻色に近い画素の重み付き平均」を取るので、
    元の絵に無い色が少し出うる（次の単純化の工程でまとまる前提）。実在の色だけにする選択肢を足すかは TODO の候補にした

## 4. パレットの色の役目と演出用の色

- **色に役目の名札を付ける**: パレットの各色に「輪郭」「目」「ハイライト」「肌」などの役目を付けておくと、パレットサイクル（色の入れ替えで動かす）や
  白く光る動きで「どの色を変えるか」を自動で決めやすい（パレットサイクルの考え方は PixelOver の解説。未確認）
- **演出用の色をあらかじめ登録する**: ダメージで白く光る・点滅などに使う色を、パレットに最初から入れておけば、
  動きの決まり「新しい色を作らない」を破らずに済む。設計の「9. 色・差し替え・重ねのトラックの見通し」の「使ってよい色」と同じ考え方

## 5. 動き

- **作らなかった理由を出力の JSON に残す**: 動きを付けなかったとき、どの決まりで止まったか・どこが問題だったかを JSON に書いておくと、
  人が絵を直すときの手がかりになる。今は CLI の警告の文言だけで、ファイルには残らない（設計の「6. 警告の出し方」の `--motion-report` の案と近い）
- **呼吸で抜くドットの条件**: 今の継ぎ目の選び方（縦に同じ色が続く所・1 ドットの線を抜かない）に、**輪郭・目・口の近くを避ける**条件を足すと、
  顔が崩れにくくなる。目・口の位置は、4. の色の役目が分かれば見つけやすい
- **まばたき**: 「開く・半分・閉じる」の絵を差し替える方法が多い。待機の動き（呼吸など）とは**別のトラック**にして、
  **数秒に 1 回**だけ再生する（毎ループではない）例が多い。設計の差し替えトラックで作るときに、
  「待機と別の周期で再生する」ことを JSON でどう表すかを決める必要がある
- **表情違いを別々に描かせて束ねるとき**: AI に表情ごとの絵を別々に描かせると、絵ごとにグリッドの位置（ずれ）が変わり、
  1 ドット＝1 画素に戻したあとで**足元の位置が揺れる**問題がある（ai-sprite-animator の話）。束ねる前に、足元（または体の大部分）の位置を
  そろえる処理が要る

## 6. 書き出しの形式

- **Godot の SpriteFrames**: アニメーションごとにフレームを持ち、フレームごとに**相対の表示時間**（基準の速さに対する倍率）を持てる。
  今の JSON の `duration_ms` から変換できる
- **Aseprite の JSON**（CLI の書き出し）: フレームごとの時間、**タグ**（フレームの範囲に名前を付けたもの。動きの名前に使える）、
  **スライス**（範囲と pivot を持てる）を持てる。将来、今の JSON に加えて Aseprite 形式でも書き出せば、Aseprite で開いて手直しする流れにつなげやすい
  （複数の動きを 1 枚のシートにまとめるときのフレームの範囲は、タグで表せる）

## 7. ゲーム側の設定

- 半端な位置（小数の座標）に置いたり、拡大率が整数でなかったりすると、ドットがぼやけたり太さがそろわなくなる。
  ゲーム側で**ピクセル単位にそろえる設定**が要る（Unity の Pixel Perfect Camera など。Godot ではテクスチャのフィルターを最近傍にし、
  ピクセル単位にスナップする設定）。`docs/cli.md` の「シートの JSON」に添えるとよい

## 8. ソースを読んだ比較（unfake・proper-pixel-art と私たちのグリッド検出）

`pip download --no-deps` で wheel を取ってきて、中の Python のソースを読んだ（unfake 1.0.7、proper-pixel-art 2.0.0。どちらも MIT）。
**どちらも OpenCV に依存している**ので、そのままでは `retrocore` で使えない（Pyodide の方針。NumPy と Pillow だけ）。取り入れるなら考え方だけを NumPy で書く。

### unfake 1.0.7（Python。一部 Rust の拡張で速くしている）

- **大きさ**: 既定では、まず「同じ色が続く長さ」（横・縦、長さ 2 以上）の最大公約数を大きさとする。1 しか出なければ、
  勾配（Sobel）の強さを列・行ごとに足したものの山の間隔から求める（画像を 3×3 のタイルに分け、タイルごとの推定の最頻値）。
  大きさは**整数 1 つ**（縦横共通）
- **位置**: 大きさが決まったあと、勾配の強さを「大きさおき」に足した合計が最大になるずれを縦横別に選び、そこから切り抜く。**格子は等間隔だけ**
- **マスの色**: 既定は、マスの中で**まったく同じ色の画素の数**を数え、いちばん多い色が一定の割合（既定 5%）以上ならその色、足りなければ平均。
  ほかに中央値・最頻・平均・左上の画素・内容に合わせた縮小（Kopf らの論文の方法）を選べる。透明は、マスの α の中央値で 2 段階にする
- **順番**: 減色（色数を決めて全体を減らす）を**縮小の前**に行う。先に色を減らすので、同じ色の画素を数えやすい
- **私たちとの違い**:
  - 私たちは周期を小数で求め、線の位置を動的計画法で不等間隔に決める。unfake は整数・等間隔なので、AI 画像のようにドットが 19〜22px に
    ばらつく入力では、端に行くほど境目がずれると見込まれる（試してはいない）
  - 色の続く長さの最大公約数は、きれいに拡大しただけのドット絵には強いが、ぼかしの名残やノイズで長さが 1 つでもずれると 1 に落ちやすい。
    そのときは勾配の方法に切り替わる（「いくつかの方法を合わせる」の素朴な形）
  - マスの色は、私たちは中心寄りの重み＋似た色をまとめて数える最頻色。unfake は完全に同じ色だけを数えるので、減色を先にしないと働きにくい

### proper-pixel-art 2.0.0

- **線の候補**: 灰色にした画像の輪郭（Canny）を少し閉じてから、Hough 変換で縦横に近い線分を拾い、近い線どうしをまとめる。画像の両端も線に入れる
- **大きさ**: 軸ごとに 3 つの推定を持つ。(1) 拾った線の間隔の中央値（外れ値を除く。間隔が十分な数あるときに優先）、
  (2) 勾配の強さの並びの山の間隔の中央値、(3) 自己相関の**最初の**山（いちばん高い山ではなく最初の山を取り、2 倍・3 倍の周期より基本の周期を選ぶ）。
  縦横の推定が近ければ平均（正方形とみなす）、大きく食い違えば小さい方を使う
- **2 倍・半分の確かめ**: 推定器が出した大きさの候補ごとに格子を作り、**マスの中の明るさのばらつき**（画素数で重み付け）で点数を付ける。
  推定値が、いちばんよい候補より決まった割合以上悪いときだけ、許容内でいちばん大きい候補に替える。
  マスを小さくすると点数は必ずよくなるので、推定器が出していない大きさは選ばない、という注意がソースのコメントにある
- **位置**: 拾った線を錨にして、その間を推定した大きさで等分し、等分した線を勾配の強さの近くの山（大きさの 35% の範囲）に寄せる。
  寄せたあと広すぎる隙間には線を足す。錨の線は動かさない。**不等間隔に追随する**が、線を 1 本ずつその場で寄せる方式
- **マスの色**: 既定は、色を区間に分けて（区間の幅 52、半分ずらした 2 通りの区切りのうち多い方）いちばん多い区間の画素の**チャンネルごとの中央値**。
  先に減色した場合は、パレット番号の最頻値。透明は、不透明な画素の割合で決める
- **私たちとの違い**:
  - 大きさの推定: 私たちは自己相関の「いちばん目立つ山」を選び、その約数の位置にも同じくらいの山があれば短い方にする。
    proper-pixel-art は推定器を 3 つ持ち、さらに**再構成のばらつきで候補を確かめる**。2 倍・半分の取り違えの確かめとして取り入れる価値がある
  - 位置: 私たちは全体でいちばんよく合う並びを動的計画法でまとめて求める（境目の無い所で 1 本ずれると次もずれる、を避けるため。設計のとおり）。
    proper-pixel-art は錨の線＋近くの山への寄せ。境目の弱い所では私たちの方が安定すると見込まれる（試してはいない）
  - 縦横: どちらも最後は正方形にそろえる。食い違ったときに小さい方を取るのは、私たちの「縦横のプロファイルを合わせて 1 つ推定する」と考え方が違う
  - マスの色: チャンネルごとの中央値は、厳密には元の絵に無い色の組み合わせを作りうる（私たちの重み付き平均と同じく、新しい色が少し出うる）
